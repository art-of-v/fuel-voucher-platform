fix(outbox): a consumer without a producer is dead code that reads like a working handler

`FulfillmentService.ProcessVoucherImportsAsync` consumed `VoucherExpired` outbox rows.
Nothing in the codebase has ever written one, and the method itself was never called
from anywhere - so it could not do anything at runtime.

What it did do was read like the code that handles voucher expiry. A reader would
reasonably conclude that expiry is handled there. It is not: the real mechanism is
`ExpiredVoucherLossService`, which flips a voucher's status, is scheduled separately
and is gated behind a setting. Two different mechanisms, and the dead one is the one
whose name says "voucher".

**The codebase already states the rule this broke.** `BulkActionVouchersCommandHandler`
says, about why it deliberately does not write a `VoucherActivated` row: *"nothing
consumes that type, so it only left permanently-unprocessed rows that inflate the admin
'unprocessed outbox events' alert"*. Writing a row nobody processes is a leak. This is
the other direction of the same rule - **consuming a row nobody writes** - and it is the
harder one to spot, because there is nothing to fail at runtime. It only shows up as a
reader's wrong assumption, which is how it survived.

**The test is the guard.** `OutboxEventTypeContractTests` scans the API project and
asserts that every outbox event type that is consumed is also produced. It fails today
without the deletion, and the failure names the type:

```
these outbox event types are consumed but never produced: VoucherExpired
```

Checked both ways: with the method present the test fails and names `VoucherExpired`;
with it deleted it passes.

**What is NOT touched**

- `OutboxEventType.VoucherExpired` stays. It is one of several enum values that are
  permitted but never written - `VoucherUsed`, `OrderCancelled`, `PaymentCompleted` and
  `VoucherActivated` are in the same position, and `VoucherActivated` carries an
  explicit comment saying it is deliberately not written. The enum is a menu of what is
  *allowed*, not a list of what happens.
- No migration. The CHECK constraint still allows the value.
- No data, no schema, no behaviour change. `ExpiredVoucherLossService` - the real expiry
  mechanism - is untouched.
