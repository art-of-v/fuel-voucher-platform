fix(ledger): the operator's renewal has no key the database enforces

A customer may renew the same voucher any number of times — the business said so
on 2026-10-20 — so a unique on the voucher alone would be wrong, and there is
deliberately none.

What there was missing is any key at all. `operator_voucher_renewals` had no unique
beyond its primary key, so a double-clicked "confirm renewal" could record the same
renewal twice: two rows, two surcharges, and a settlement discrepancy somebody
reconciles by hand three months later.

**The key is (voucher, the expiry it was moved to).** A repeated request produces the
*same* new expiry, so the constraint catches it; a genuine second renewal is to a
*later* expiry, so it is a different key and is allowed — which is exactly what the
business rule requires.

**Why the database and not the handler.** The handler checks the voucher's current
expiry first, so a second confirmation is already refused by the application — which
means the application check is the *common* case, not a guarantee. The check and the
write are not in the same atomic step, so it is a race. The race is won by the index,
and only the database can settle one. Together with
`ck_operator_renewal_expiration_moves_forward`, which is already in place, both
halves are covered: the one where the voucher's expiry was already moved (the check
catches new == old), and the one where it was not (this index catches the same
target).

**The exchange half was already there.** `voucher_exchanges.old_voucher_id` carries
a unique index (`ix_voucher_exchanges_old_voucher_id`), so a voucher cannot be
exchanged twice. The review's F-10 said it had no unique constraint at all; that
was read off `pg_constraint`, which does not list unique *indexes*. Correcting the
record matters, because a finding that says "there is no constraint here" sends the
next reader looking for a problem that is not there.

**The test writes to the table directly, on purpose.** Through the handler, a
repeated confirmation is refused by the application — so a handler-level test would
pass with or without the index, and prove nothing. Only the database is asked.
Checked both ways: with the index the test passes; with the index not created the
test fails with *"expected a DbUpdateException to be thrown… but no exception was
thrown"*.
