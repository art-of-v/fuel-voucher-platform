fix(migrations): a Down that does not undo its Up, and a test that would have caught it

The migration that added the renewal's idempotency key had a `Down` that CREATED
the index instead of dropping it. A text replacement while authoring the migration
had rewritten both halves, and the restore put `CREATE` back into both.

The symptom was a CI failure in a test that rolls the schema back:
`42P07: relation "ix_operator_voucher_renewals_voucher_id_new_expiration" already
exists`. The symptom in production would have been worse and later: the history is
append-only, so a migration with a broken `Down` cannot be rewritten — it can only
be worked around with another migration, and nobody finds out until somebody rolls a
schema back, which is exactly what a broken deployment needs.

**The new test rolls the newest migration back and forward again.**
`MigrationReversibilityTests` takes the last two migrations, migrates to the one
before the last, and migrates to head — so the newest migration's `Down` and `Up`
are both exercised on every run. The schema is returned to head in a `finally`, so
one failure cannot cascade into the next test.

Checked both ways: with a correct `Down` it passes; with the `Down` this commit
fixes it fails with the same `42P07` the CI run produced.

**The test is not a nicety here.** The repository already had a test that rolled the
schema back - `SeededBrandIdsAreDerivedTests` - and it is the one that failed. What
was missing was a test that rolls back **the newest** migration, which is the one
nobody has ever tried.
