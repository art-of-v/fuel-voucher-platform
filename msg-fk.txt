fix(schema): the foreign keys the columns were pretending to have, and the indexes under them

Twenty-seven uuid columns were named like references and enforced by nothing. This adds
the foreign keys that the schema was shaped as if it had, and the indexes under them —
and it is explicit about the ones that stay without a key, because the rule that
excludes them is written down and worth keeping visible.

**The rule the schema now follows, in one place**

| what the column means | foreign key | ON DELETE |
|---|---|---|
| the child belongs to the parent and dies with it | yes | CASCADE |
| the child is a business fact about the parent | yes | RESTRICT |
| the author of the record, and the record must survive the author | yes | SET NULL |
| the author of the record, and the author IS part of the record | yes | RESTRICT |
| an audit row — it must not be the thing that blocks deleting its own subject | **no** | — |
| polymorphic, or a grouping key rather than a reference | **no** | — |

**What gets a key.** Fourteen: `order_line_items.fuel_type_id`,
`purchase_batches.fuel_type_id`, `payments.webhook_event_id`,
`operator_voucher_renewals.customer_user_id` and `.acting_user_id`, `users.party_id`,
`feedback_chat_bindings.user_id`, `feedback_messages.user_id`, `error_logs.resolved_by_user_id`,
`fuel_price_history.changed_by_user_id`, `fuel_types.price_updated_by_user_id`,
`settlement_messages.resolved_user_id`, `app_settings.updated_by_user_id`,
`provider_event_outbox.changed_by_user_id`.

Every one of them was measured against the live database first. Eleven were clean; two needed
attention before a constraint could go on them.

**The outbox's author was not a user.** `provider_event_outbox.changed_by_user_id` was NOT
NULL, and the price sync wrote the **all-zero guid** into it — 35 of its 74 rows. A value
that stands for "no user" is not a user, which is exactly why the column could have no
foreign key at all. The system writes NULL for a machine event now, the sentinel rows are
normalised, and the column carries a key with SET NULL. The name survives in
`changed_by_user_name`, so nothing about who did it is lost.

**What stays without a key, and why.** The audit actor columns — `voucher_events.actor_*`,
`voucher_movements.actor_*`/`.order_id`/`.line_item_id`, `order_events.actor_user_id`,
`movement_batches.opened_by_user_id` — are the ones the code deliberately leaves bare, and the
code says why: *"a ledger that gets deleted is not a ledger"*, and the cleanup job that
deletes an unpaid order would wedge on the same key `order_line_items.order_id` already
wedges it on. `journal_entries.source_id` is polymorphic — `source_type` says what kind of row
it is — and `refresh_tokens.family_id` is a grouping key, not a reference: every one of its
852 rows points at a family that is not itself a row, and `Guid.Empty` is its "no family".

**The indexes.** PostgreSQL does not create one for a foreign key, so the constraint is
checked by scanning the child table on every delete of the parent, and every join down that
column scans too. Sixteen were added — the fourteen key columns and the two that already
had one.

**The tests are about the schema, not about the fourteen keys.** `ForeignKeyContractTests`
asserts that every foreign key the model declares is in the database **with the same delete
rule**, that every foreign key column in the database has an index, and that the outbox's
author column is nullable and carries no sentinel. A key the model declares and the database
does not have is invisible — the model looks right, the database is unguarded, and nothing
fails. So the test is a property of the whole schema, which is the part that catches it.

**One thing this does not do.** `refunds` has three such columns, and they are left alone:
the table is **legacy** — the model stopped mapping it when refunds were absorbed into
`payments` as a `kind` — so a foreign key on it would enforce something nothing writes.
Dropping the table is a separate piece of work, and it is now on the list.
