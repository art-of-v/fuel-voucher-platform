fix(suppliers): the registry code is optional, and unique when it is there

The previous change made the supplier's registry code mandatory, and that was wrong:
the business's rule is that a supplier can be recorded before anyone has looked the
code up. Requiring it would mean a supplier who cannot be invoiced cannot be bought
from either.

**What is right:**

- **Optional.** The column stays nullable, the API accepts a blank, the form asks for it
  but does not insist.
- **Unique when it is there.** Two rows with the same code are the same counterparty
  recorded twice, and a business that pays "two" suppliers who are one person pays
  twice and reconciles the difference by hand. A code that is not there cannot collide,
  so the uniqueness costs nothing for a supplier who has not been identified yet.
- **A code that is given has to be a code** - 8-10 digits, checked in the database as
  well as in the API. A blank is stored as NULL rather than as an empty string, so the
  constraint never sees one: a supplier with no code is allowed, a supplier with a blank
  "code" is not.

**The migration is regenerated rather than corrected in place.** The one that made the
column mandatory would have refused to run on any database with a supplier that has no
code - and it had never been applied anywhere, so it was replaced rather than
half-fixed. It created the index and the constraint and changed nothing else.

**Checked:** the API accepts a supplier with no code and with a blank one, and stores
both as null; the database accepts a supplier with no code, refuses two suppliers with
the same one, and refuses a code that is not a code.
